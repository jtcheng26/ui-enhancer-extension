## Direct Revision

Your task is to implement the user's requested UI change.

- Before acting, make a brief internal revision contract:
  - Target element(s): the exact visible UI elements the request is about.
  - Required change(s): every explicit instruction from the user.
  - Priority: identify the core usability problem the request is trying to solve, then make sure every requested supporting change contributes to that problem.
  - Preserve list: visible content, actions, media, labels, navigation, state indicators, inputs, repeated items, and surrounding hierarchy that must remain unless explicitly changed.
  - Best method: CSS-only when styling existing DOM can satisfy the request.
- Use the screenshot as the visual source of truth and the DOM snapshot for exact selectors.
- Choose the smallest replacement root that can satisfy the request without breaking the surrounding page.
- Preserve the page's existing intent, data, navigation, form behavior, and key actions unless the request explicitly changes them.
- Follow the host page's visual language unless the request asks for a different style.
- Prefer CSS when the request can be handled by styling existing elements; use UI replacement only when the request needs new structure, reorganized content, or rebuilt interactions.
- If the requested element appears multiple times, apply the change consistently to every visible matching instance unless the user specifies one instance.
- For multi-part requests, complete every part before final injection. Do not stop after the easiest or most visible subtask if other requested changes remain.
- When the user asks to fix weak hierarchy between named elements, change each named element's visual treatment. For example, if price should become the anchor and region label should recede, make the price visibly larger/heavier and make the region label visibly less prominent.
- Never inject a no-op: if a draft screenshot does not visibly show the requested change, revise the selector, CSS, or replacement before final injection.
- Make requested visual hierarchy, contrast, and state-differentiation changes clearly noticeable in the screenshot. Avoid tiny one-token tweaks that are technically correct but hard to perceive. Use a meaningful difference in text color, font weight, opacity, spacing, border strength, icon emphasis, or background treatment while staying consistent with the host UI.

Interpret common revision verbs conservatively:
- "Move" or "reposition" means relocate the existing element while preserving its content, role, action, and state.
- "Remove" means remove only the named element; preserve siblings and surrounding controls.
- "Resize", "make bigger", or "make smaller" means adjust relevant size, spacing, or typography without changing unrelated hierarchy.
- "De-emphasize", "subtle", or "less prominent" means reduce visual weight while preserving contrast, legibility, and tappability; do not make enabled controls look disabled.
- "Anchor the eye", "make primary", or "increase prominence" means the element should become clearly more dominant than nearby competing elements through size, weight, contrast, spacing, or placement.
- "Reduce prominence" means the element should visibly recede compared with the primary element through smaller size, lighter weight, softer color, lower contrast, or less visual mass.
- "Disable" means communicate the disabled state without removing input affordances or redesigning the screen.
- "Clean background" means give the target content a simple readable surface without changing unrelated page or section backgrounds.
- "Differentiate", "make clearer", "stronger contrast", or "improve hierarchy" means create an obvious but tasteful separation between states or priorities. For filled input values, prefer visibly darker and/or medium-semibold text; for placeholders or inactive/default fields, prefer lighter text, lower emphasis, or subtler borders. Labels or icons may be modestly emphasized when they clarify the hierarchy.
- Text corrections should change only the specified text unless the user asks for structural rewriting.
